# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — dev server
- `npm run build` / `npm start` — production build/serve
- `npm run test` — Vitest (all suites live under `lib/**/*.test.ts`); a single file: `npx vitest run lib/classify.test.ts`
- `npm run db:generate` — regenerate Drizzle migrations from `lib/db/schema.ts` (the hand-written FTS5 migration, `db/migrations/0001_fts5.sql`, is NOT schema-derived — see below)
- `npm run db:migrate` — apply migrations to `$DATABASE_PATH` (defaults to `./data/skills.db`)
- `npm run refresh` — run the GitHub refresh pipeline once (`scripts/refresh.ts`)

Tests run against an in-memory SQLite DB (`DATABASE_PATH=:memory:`, set in `vitest.config.ts`), isolated per test file.

## Architecture

**Data flow**: `scripts/refresh.ts` and `POST /api/refresh` are both thin callers of `lib/refresh.ts::runRefresh()`, the only code that talks to GitHub (via `lib/github.ts`). Everything else — the directory page, detail pages, `/api/repos` — reads only from SQLite via `lib/query.ts`. Never call the GitHub API from a page or the `/api/repos` route.

**FTS5 is not a Drizzle schema object.** `db/migrations/0001_fts5.sql` is a hand-written migration (not generated by `drizzle-kit generate`) creating an external-content virtual table (`content='repos', content_rowid='id'`) plus `AFTER INSERT/UPDATE/DELETE` triggers that keep it in sync automatically whenever Drizzle writes to `repos`. If you regenerate migrations after a `schema.ts` change, `db:generate` won't touch or remove this file — but check the new migration doesn't conflict with it. Search goes through `lib/db/fts.ts::ftsMatchIds()` (raw SQL against `repos_fts`) and back into a normal typed Drizzle query in `lib/query.ts::queryRepos()`.

**Refresh pipeline** (`lib/refresh.ts::runRefresh()`, accepts an injectable `GithubClient` for testing): gathers candidates from topic/keyword search + a seed list + awesome-list README scraping, classifies and extracts fields per repo, upserts by the stable `github_id` (idempotent — safe to re-run), then does a removal pass. A repo is only marked removed after **two consecutive** confirmed-missing runs (`removedMissCount`), to avoid flapping on a transient search-result miss. A `RateLimitError` from `lib/github.ts` stops whatever phase it's in and marks the run `partial` rather than failing the whole thing.

**Classification** (`lib/classify.ts`) is priority-ordered and pure/testable: `SKILL.md` (root or subfolder) beats MCP-shaped name+manifest, which beats explicit topic tags, which falls back to `unclassified` (surfaced in `/admin`, never guessed). Subfolder `SKILL.md` detection needs `GITHUB_TOKEN` (uses the code search API, which 401s unauthenticated).

**README storage**: `repos.readmeExcerpt` stores raw (bounded, ~4000 char) markdown, not stripped text — it's rendered + sanitized at read time via `lib/sanitize.ts` (`marked` + `sanitize-html`) on the detail page. `purposeSummary`, by contrast, IS derived via `lib/extract.ts::stripMarkdown` + paragraph extraction, since it's a plain-text summary rendered as normal JSX text (React escapes it automatically — no sanitize-html needed there).

**Trending / "New"**: `star_history` records one snapshot per repo per refresh run; `trending7d`/`trending30d` are recomputed each run by diffing current stars against the nearest snapshot older than the cutoff. "New" isn't a stored flag — a repo is new if `firstSeenRunId` is among the last 8 `refresh_runs` rows (`lib/query.ts::getRecentRunIds()`), so the window tracks actual runs, not wall-clock time.

**Auth**: one shared `ADMIN_TOKEN` (see `lib/auth.ts::isAuthorized`) gates `POST /api/refresh`, `PATCH /api/admin/repos/[id]`, and `GET /api/repos?includeHidden=1`. No user accounts.

**Frontend**: filter/search/sort/view state lives entirely in the URL (`FilterBar.tsx`), read directly by the Server Component `app/page.tsx` — there's no client store. `app/page.tsx`, `app/repo/[owner]/[name]/page.tsx`, and `app/admin/page.tsx` are all `force-dynamic` (they read live DB state per-request; do not remove that export or Next will try to statically prerender them at build time, before any data exists).

**Deployment constraint**: `better-sqlite3` needs a persistent writable filesystem. This app is meant to be self-hosted (Docker/VPS) — it will not work correctly on serverless platforms with ephemeral filesystems (Vercel/Netlify functions).

## Known limitation

`notFound()` on `/repo/[owner]/[name]` renders the correct not-found UI but returns HTTP 200 instead of 404, even in a production build — this is a Next.js 14 App Router quirk with nested dynamic segments, not application logic. Low priority to fix (cosmetic status code only, content is correct).
